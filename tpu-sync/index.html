Three maps, one working mental model

The repository is easier to navigate when each arrow has a job. A compiler transforms a program. A runtime manages resources. A build system assembles binaries.

Choose a map, then select a component. The runtime map follows references to one allocation; its boxes do not imply five full tensor copies.

Your initial working set: tensor → base storage → physical byte ranges → registered host memory → copy → completion. Learn the compiler boundary well enough to respect its layout and readiness decisions. Add deeper compiler internals only when your change requires them.

A 90-minute framework warm-up

  1. 15 min: sort the three graphs; explain why “depends on XLA” does not mean “every copy compiles.”
  2. 20 min: learn PJRT's six handles; attach identity, representation, lifetime, readiness, and completion to actual code.
  3. 25 min: trace the Python loader → binding → at::Tensor → base buffer → manager/raw copy chain.
  4. 20 min: inventory the environment without changing it; record Python/Torch/TorchTPU/libtpu versions, repo revision, TorchTPU XLA pin, and selected extension ABI.
  5. 10 min: choose a symptom from the table and predict the first file to open.

Pass condition: explain both cache = cpu_tensor.to("tpu") and manager.h2d(...), including who owns the representation conversion, without using “XLA” as a catch-all noun.

The rest of this handbook preserves the original eight-session data-plane plan. Budget roughly 14–18 hours including the new framework foundation.

PJRT objects: handles, not hardware boxes

Handle Think of it as Question it answers
PjRtClient Runtime session, owning device/memory-space objects Which backend and resources am I using?
PjRtDevice A runtime-visible execution location Which device can execute this work? Is it addressable by this process?
PjRtMemorySpace A runtime-described memory location Where may this buffer live, and which devices access it?
PjRtBuffer Owned data plus metadata/readiness Which allocation contains these values?
PjRtLoadedExecutable Compiled work loaded for execution What program consumes/produces those buffers?
Future / PJRT_Event Completion and status Is the promised result ready, and did it succeed?

These are CPU-side handles, not hardware boxes. A buffer can exist before its contents are ready. Do not infer that every hardware memory level is exposed as an allocatable PJRT memory space: VMEM inside a compiled kernel is a separate scheduling concern. PJRT component overview.

The repo's RaidenBufferHandle adds exactly what generic transfer code needs: physical geometry, device, copy methods, and an owner/hold. Raw aliases do not magically validate model-level dependencies. The held reference solves ownership; the appropriate readiness/completion edges solve ordering. Raw handle.

Eager does not mean compiler-free

Google TorchTPU offers debug eager (synchronize per operation), strict eager (asynchronous dispatch), and fused eager (group operations). These modes change grouping and submission; eager operations can still involve compilation. With torch.compile, TorchDynamo captures an FX graph, TorchTPU lowers operations toward StableHLO, and XLA produces executable work. This is a conceptual path, not a claim that each tensor copy traverses every stage. TorchTPU architecture.

Five words that unlock most of the code: lowering translates a program into a representation closer to execution; materialization resolves pending work into usable backing storage; aliasing refers to existing storage; registration makes a host range usable through the device DMA interface; completion reports whether an operation finished successfully. None substitutes for the others.

02

One tensor, two host-to-device paths

Follow two operations that both end with bytes in HBM. Their representation contracts differ.

Path A · initial placement

cache = cpu.to("tpu")

  1. The CPU tensor contains logical values in a CPU layout.
  2. TorchTPU creates or supplies compatible device storage and arranges the placement through its runtime.
  3. The framework establishes the device representation; it may need layout conversion.
  4. Subsequent computation must respect the result’s readiness.

The semantic contract is “these values on this device.” Do not assume every implementation does one CPU memcpy followed by one DMA.

Path B · raw restore

manager.h2d(...)

  1. The manager already refers to the live cache allocation.
  2. Host slots contain a compatible physical snapshot.
  3. Block indices become offsets and lengths; raw DMA writes the existing allocation.
  4. A successful future/event establishes copy completion before the next consumer.

The semantic contract is “put these device-compatible bytes in this existing storage.” It does not imply automatic conversion from arbitrary CPU tensors.

The Torch manager recovers the PJRT client from the existing TorchTPU device buffer. It does not establish a separate device runtime for each block. The raw-buffer extension accepts a host pointer, device offset, and length, and the C-API path returns an event. The TPU implementation is reached through TorchTPU and its libtpu dependency.

Client extraction · Raw copy/event boundary · libtpu dependency

Why the compiler still matters to the copy engine

A raw transfer usually does not compile a fresh program. But the destination’s layout, allocated size, and pending producer work can originate from compiled execution. The copy engine inherits those contracts. This is why “XLA is only for compute” is too simple, and “every copy goes through the entire compiler” is also misleading.

During graph execution, a buffer can be promised before its contents are ready. During raw restore, the buffer can be alive while a different operation still reads it. Track identity, representation, ownership, and ordering independently.

Read the dependency tree with a purpose

Read three vertical slices: call surface (api/torch + nanobind), storage and copies (frameworks/torch + core + relevant kv_cache), binary integration (build.sh + wheel/module shims). Keep transport as the next slice after single-host correctness. Put IFRT/JAX, distributed placement, RPC registry, and dashboards on a later-reading shelf unless a change crosses their boundary.

The code deliberately separates framework-specific extraction from generic movement. A new framework adapter should satisfy those contracts instead of teaching the transport about framework tensor classes. API, ABI, and why the loader looks complicated

An API is the source-level contract. An ABI includes binary conventions such as symbols, layouts, calling conventions, and virtual function tables. Two headers can look similar while the resulting shared libraries disagree about a C++ object's representation.

This is a concrete repo constraint: TPU Sync invokes C++ virtual methods on PJRT objects created by TorchTPU. build.sh torch resolves the XLA revision embedded in the TorchTPU wheel/check-out and builds against it, with this repo's patches. MODULE.bazel's default XLA pin follows the JAX leg. The script warns that a combined JAX+Torch build has only one XLA module and cannot express both pins, and requires Torch-only release builds. Exact explanation.

There is a second boundary: both TorchTPU and TPU Sync can contain independently built XLA C++ code. Passing xla::Future/tsl::AsyncValue across that boundary is fragile; the raw TPU completion path therefore uses PJRT C events. This stabilizes that completion boundary; it does not erase every other C++ ABI dependency. C-event rationale.

There is a third boundary: shared-library symbol lookup. The wheel build uses TorchTPU headers without linking a duplicate implementation, then patchelf adds a NEEDED entry for the matching TorchTPU glue library. The loader uses local scope, avoiding duplicate XLA allocator registration caused by globally preloading runtime symbols. Copying a .so from another Torch build or changing RTLD_LOCAL to RTLD_GLOBAL can break this carefully chosen arrangement. Header-only build boundary, linking explanation, loader.

Start with the physical machine

A fast arithmetic unit needs a continuous supply of operands. Large memories provide capacity; nearby small memories provide cheaper, faster reuse. Transfers and reuse connect the two. This gives us the questions to ask before opening any class definition: Where are the bytes now? Where will the next consumer execute? How much must move? In what representation? What proves the move is finished?

This is a conceptual dense-tensor path, not a complete wiring diagram. TPU Sync operates primarily across the host DRAM↔HBM boundary. It does not implement the attention kernel's HBM↔VMEM pipeline. Keep those two transfer problems separate while learning how their performance interacts.

Scope v7x fact to keep in your notebook
Physical package Two chiplets; 192 GiB aggregate HBM; about 7.38 TB/s aggregate HBM bandwidth
Chiplet / TensorCore Separate memory space; about 96 GiB HBM and 3.7 TB/s HBM bandwidth
On-chip memory per TensorCore 64 MiB VMEM and 1 MiB SMEM
Host VM Four physical packages, two NUMA nodes, 960 GB host RAM
Device enumeration Frameworks such as JAX expose two devices per package; inspect your TorchTPU/PJRT visibility rather than inferring it from a machine name

The capacity table uses GiB; some Cloud prose uses “GB” inconsistently. A package's aggregate HBM is not one chiplet's allocation budget. HBM bandwidth, host PCIe bandwidth, and ICI bandwidth measure different links. Cloud TPU7x architecture, JAX TPU hardware reference.

VMEM is explicitly managed SRAM. Its physical capacity does not grow when you change the compiler's scoped-VMEM allocation limit; that budget also interacts with prefetch use. Ironwood optimization guide.

For architecture background, read the memory and DMA discussion in the Google authors' TPU architecture paper. HBM↔VMEM movement is scheduled, with asynchronous DMA and completion mechanisms. The payoff is predictable operand supply and reuse; the cost is that layout, working-set size, and scheduling matter. Your familiar “load once, reuse many times” instinct survives the trip from CUDA.

S1

The memory hotel: the penthouse has a tiny kitchen

HBM is the warehouse; VMEM is the kitchen counter; registers hold the ingredients currently being used. Host DRAM is the warehouse across town. Renting more storage across town does not make every meal faster.

Start with two calculations. For an illustrative unsharded cache with 32 layers, 8 KV heads, head dimension 128, and BF16:

KV bytes/token = 2 (K and V) × 32 × 8 × 128 × 2 bytes
               = 131,072 bytes = 128 KiB
8,192 tokens   = 1 GiB of KV
256 tokens    = 32 MiB across all these layers

These are model-wide bytes. Derive the local shard's payload before making per-device claims; sharding and replication can change it.

Now suppose you measure 25 GB/s for one particular host-transfer scope. That is a hypothetical input, not a v7x specification. A 1 GiB one-way transfer has a bandwidth-only time of about 42.9 ms; offload plus restore costs about 85.9 ms before overhead. At 3.7 TB/s, the same byte count divided by chiplet HBM bandwidth is about 0.29 ms. Neither number is a complete kernel latency. The comparison explains why repeatedly leaving HBM can be expensive.

Read: the hardware sources above, then the narrow overview of raw transfer. Treat the older raw-transfer document as orientation; later sessions distinguish its JAX examples from current Torch behavior.

Exercise: draw three independent arrows: host↔HBM, HBM↔VMEM, and accelerator↔accelerator fabric. Write capacity next to memory boxes and bandwidth next to links. Do not attach “7.38 TB/s” to the host arrow.

Pass condition: explain why offloading can improve capacity or avoid recomputation while still adding transfer latency. Estimate whether restoring a cached prefix costs less than recomputing it.

To connect this back to VMEM, consider a toy square matrix multiply of tile width b. Loading two BF16 input tiles costs 4b² bytes; the multiply performs roughly 2b³ floating-point operations. Ignoring output traffic and other overhead, reuse gives b/2 FLOP per input byte. Larger tiles improve this ratio but consume more SRAM. Two sets of 1024×1024 BF16 inputs for double buffering plus one FP32 output occupy 12 MiB before workspace. The point is the tradeoff: retain and reuse operands near compute, while leaving room to stage the next work. This is arithmetic for a teaching model, not a prescribed v7x kernel configuration.

S2

A tensor's secret floor plan

A tensor has logical coordinates, dtype, shape, and strides. A device allocation has a physical layout, possible padding, and byte capacity. DMA receives addresses and lengths. It does not reconstruct tensor semantics for you.

There are two useful meanings of “transfer from host.” Initial placement with cpu_tensor.to("tpu") gives the framework logical CPU values and lets it arrange device storage. A raw manager.h2d(...) restore gives the DMA path bytes already compatible with that destination's physical representation. Capturing them with D2H supplies that representation; inventing ordinary row-major CPU values does not. The optional weight-synchronization chapter shows explicit packing when conversion is needed.

Why tile at all? Grouping operands consumed together into regular storage regions can simplify bulk movement and local reuse. Padding spends capacity and bandwidth to preserve regular geometry. That is the performance rationale; the runtime's actual layout remains the authority. An MXU compute tile, a vector-register shape, an allocation's XLA tiles, and a transfer's alignment requirement are separate choices.

Use the repository's toy 6×6 FP32 matrix tiled into 4×4 tiles. Logical size is 6×6×4 = 144 bytes. Padding to 8×8 requires 8×8×4 = 256 bytes. The physical footprint is about 1.78 times the useful data. This is a teaching layout from a test, not a universal v7x tile size. Padding2D test.

For this toy, with row-major order both between and within tiles:

tile_id(r,c)   = floor(r/4) × 2 + floor(c/4)
inside(r,c)    = (r mod 4) × 4 + (c mod 4)
byte_offset   = 4 × (tile_id × 16 + inside)

Element (4,1) lives at byte 132, whereas an ordinary unpadded row-major array would place it at byte 100. Same logical value; different address arithmetic. An ordinary CPU float view of raw device bytes can therefore look wrong even when the DMA is perfect.

Read: GetMajorSliceByteSize and ValidateMajorDimLayout. The former accounts for supported tiled minor dimensions. The latter checks assumptions needed to address a buffer as consecutive leading-dimension slices.

There are two paths to keep distinct:

Path How it obtains copy geometry
Standalone Torch raw batch helpers GetMajorSliceByteSize, layout validation, chunk construction; partial-copy checks include rank ≥3 and 4096-byte slice alignment
KV manager used in this course Actual per-layer physical allocation bytes divided by its block count; that layer's row width indexes device and host buffers

Those are implementation contracts. The 4096-byte check is not a definition of TPU VMEM, an MXU tile, or every transfer API's granularity. Partial-copy validation, manager physical row sizes.

Exercise: calculate offsets for (0,0), (3,3), (4,1), and (5,5) in the toy. Mark padding. Then read a real shape/layout from the runtime before attempting an equivalent calculation for a TPU tensor.

S3
The storage passport: the address must belong to the live cache
Follow this chain in UnpackTorchTensor:


Torch Tensor
  → validate device, contiguity, offset, full-storage view
  → GetBaseTensorBuffer(tensor)
  → Materialize() the base if deferred
  → AwaitBuffer()
  → acquire RaidenBufferHandle
  → keep the owning TensorBufferHandle



The pivotal word is base. A layout-changing view may materialize as a separate allocation. Copying restored KV bytes into that allocation would succeed as a memory operation while failing as a cache update: the model still reads the original storage. The adapter deliberately finds that original storage.


The inspected adapter requires PrivateUse1 tensors, contiguity, zero storage offset, and a nonempty leading block dimension. It checks full-storage coverage and compatible base/view dimensions, with a specific rank-1 raw-storage→rank-2 block-view allowance. It does not support arbitrary sliced or reshaped tensors merely because PyTorch calls them contiguous.


Materialization solves another problem: a deferred allocation or operation must be submitted before an await can finish. Read the lazy-cache construction regression test. The lesson is to resolve the actual storage's pending work without accidentally manufacturing a replacement buffer.


RaidenBufferHandle then hides two runtime forms: CommonPJRT raw buffers with holds, and C-API raw aliases with an owning wrapper. Copy code gets a common vocabulary for shape, device, raw copy, and lifetime. This is a boundary between framework/runtime integration and byte movement. Raw buffer abstraction.


Exercise: annotate each call with “identity,” “readiness,” “geometry,” or “ownership.” Find one line that solves each problem. Explain what would break if you returned only a naked PjRtBuffer*.


Pass condition: answer this interview trap: “The tensor is contiguous and its Python variable is alive. Is raw DMA therefore safe?” Answer: those facts alone do not establish the correct base allocation, compatible physical layout, or producer/consumer ordering.


S4
Booking host memory: an address is not a DMA reservation
Trace the production host allocator in host_memory_allocator.cc. Its ordinary XLA allocator rounds the allocation up to a page boundary, uses mmap, registers it using PjRtClient::DmaMap, and returns a pointer, size, and shared owner. The owner's cleanup calls DmaUnmap and munmap.


This is why HostBufferAllocation is more informative than void*: the pointer says where; the size bounds access; the owner says how long the mapping remains valid and how to release it. Allocation interface.


The device-aware path attempts NUMA-local allocation using a memory policy and page touches. Locality depends on successful topology resolution and the environment; inspect the policy and logs before claiming the placement worked. A buffer can be registered correctly yet still suffer an expensive cross-socket path.


The separate RawHostBuffer abstraction first tries a PJRT pinned_host memory space, then falls back to the host allocator. Both routes aim to provide useful host staging, but they are not the same construction path. RawHostBuffer binding implementation.


Why keep a pool? Registration and allocation have setup costs. Reusing registered regions amortizes them and makes steady-state transfers easier to pipeline. The cost is reserved host capacity and the obligation to track when a slot can be reused. This is design reasoning from the implementation, not a claim that registration is free or that all host pointers take the fast path.


Exercise: draw allocate → map → transfer(s) → completion → unmap → free. Attach every step to its owner. Explain why mmap, page alignment, residency/pinning, and DMA registration are related but different concepts.


Optional: inspect shared-memory allocation. /dev/shm can preserve bytes across a process restart when the backing segment survives, but it is still volatile host RAM, not disk persistence. A new process must establish its own mappings/registration and validate compatibility. Stop before studying recovery orchestration.


Pass condition: explain both the correctness reason and the throughput reason for retaining registered host memory until every user has completed.


S5
The block shuffle: one parcel, several addresses
Read the Python d2h/h2d wrappers, the Torch adapter's manager construction, and the core copy submission path.


For layer l, let R_l be its physical bytes per block. A local restore of n consecutive blocks is conceptually:


source pointer     = host_base[l,shard] + source_host_block × R_l
destination offset = destination_device_block × R_l
length             = n × R_l



Host block 1 need not contain device block 1. Those IDs name different spaces. Layers may also have different row widths, so borrowing layer 0's byte stride for every layer corrupts heterogeneous caches. The manager computes per-layer widths and allocations. Per-layer initialization.


The following is an unrun hardware lab, adapted to the inspected Python signatures and a shape used by the repository's Torch tests. Run it only after installing the matching Google TorchTPU and built TPU Sync extension. It uses one visible TPU device and serial waits; it is a correctness exercise, not a bandwidth benchmark.


import torch
import torch_tpu  # Google TorchTPU backend registration
from tpu_sync.api.torch.kv_cache_manager import KVCacheManager

# A position-dependent pattern exposes swaps that constant fills can hide.
shape = (4, 128, 8)
reference = torch.arange(4 * 128 * 8, dtype=torch.float32).reshape(shape)
cache = reference.to("tpu")
torch.tpu.synchronize()  # Finish producers before entering the raw-copy lab.

manager = KVCacheManager(
    kv_caches=[cache],
    local_control_port=0,
    max_blocks=4,
    num_slots=1,
    unsafe_skip_buffer_lock=True,
)

# The caller provides exclusive access here: no concurrent model work,
# no rebinding/mutation of cache storage, and every copy is awaited.
manager.d2h(src_offsets=[0, 2], dst_offsets=[0, 1]).Await()

snapshot = manager.read_block_bytes(layer_idx=0, block_id=0)
print("raw bytes in one host block:", len(snapshot))
# snapshot is an opaque device-layout snapshot, not a CPU float array.

manager.h2d(src_offsets=[0, 1], dst_offsets=[1, 3]).Await()

expected = reference.clone()
expected[1] = reference[0]
expected[3] = reference[2]
actual = cache.cpu()  # Framework conversion for semantic verification.
torch.testing.assert_close(actual, expected, rtol=0, atol=0)
print("PASS: blocks 1 <- 0 and 3 <- 2; untouched blocks preserved")



The port argument satisfies construction; networking is not part of this lab. The explicit unsafe setting makes the caller's ordering obligation visible. Changing a lock flag alone does not establish every model/transfer dependency.

S6
Async without wishful thinking
There are three separate promises:


    

  1. Lifetime: the storage still exists.
    2. 

  2. Readiness: the producer has finished writing the source.
    3. 

  3. Exclusivity and ordering: no conflicting access occurs during the transfer, and the consumer starts after completion.
    4. 



A shared pointer mostly answers the first. A completed transfer future answers a particular operation's completion. Neither means every possible writer or reader is correctly ordered.


producer completes

submit D2H ─────────────→ D2H completes
                              ↓
                  host snapshot may be consumed
                              ↓
submit H2D ─────────────→ H2D completes

Read PjRtCopyFuture and raw event handling, then IssueD2hShard/IssueH2dShard. Trace which owners are retained and which operation the completion represents. The manager keeps base-storage references for its lifetime; transfer objects/futures retain additional state as needed. Keep managers, buffers, and futures alive and explicitly await all outstanding work in the first labs.


There is a software-engineering reason for the PJRT C-event path: TorchTPU and TPU Sync can embed independently built XLA C++ code. Passing C++ futures across that boundary risks ABI mismatches. The code explicitly uses the C event boundary for this case. It is an integration constraint, not a property of HBM. The standalone prepared raw helper follows a different wrapper path, so read the entry point actually used. C-event rationale.


Exercise: draw a two-slot staging ring. Slot 0 carries block A while slot 1 carries block B. Mark the exact completion required before either slot can be overwritten. If a network send also reads a host slot, its completion matters too.


Then design overlap with independent compute: prefetch block n+1 while attention consumes block n, waiting before first use. Confirm overlap with a trace. “Async” in a method name proves neither concurrent hardware progress nor a speedup.

S7
The bandwidth detective: the tiny-parcel tax
Model an isolated transfer as T(S) ≈ α + S/B, where α includes fixed submission/synchronization costs and B is payload bandwidth for a stated scope. With illustrative α=10 µs and B=25 GB/s, a 4 KiB transfer takes about 10.16 µs and achieves only 0.40 GB/s. Bigger or coalesced work amortizes the fixed cost.


Coalescing is valid when the source and destination runs both continue contiguously. Adjacent source blocks sent to unrelated destination slots are not one ordinary contiguous DMA. A good experiment separates payload size, number of ranges, and allocation setup.

S8
The scenic route, plus the capstone
The repository's cross-node benchmark explicitly describes this route:



It is called device-to-device because of its endpoints. That does not establish a direct ICI or NVLink-like path. TPU documentation also uses “D2D” for die-to-die links, which is yet another meaning. Read the benchmark's route description and host socket transport; follow payload pointers rather than names.


For a serialized payload of size S, model:


T ≈ S/B_D2H + S/B_network + S/B_H2D + overhead



With enough independent chunks and actual overlap, steady-state throughput is bounded by the slowest stage. Shared host-memory traffic, copy overhead, PCIe contention, and limited staging slots can tighten that bound. Pipelining reduces idle time; it does not erase the bytes traversing each stage.


Now look at PoolSpec and RegionSpec. A pool names storage, a base, block stride, and live regions. This lets generic transfer code handle different model-state layouts without understanding attention heads or recurrence equations. The model integration supplies semantics; the byte engine supplies bounded movement.


The Swiss-cheese exercise: pool base 8, block stride 128, and two 16-byte live regions at offsets 0 and 32. Blocks 0 and 1 produce (offset,length) pairs (8,16), (40,16), (136,16), (168,16). Live payload is 64 bytes; the last extent ends at offset 184. Payload size, address span, and allocation capacity differ. Extent computation and tests, pool layout implementation.


Optional representation chapter: raw KV snapshots preserve physical layout because the restore consumer needs those same bytes. Weight synchronization sometimes needs a different contract: weight_synchronizer_base.cc calls TileBuffer before H2D and DetileBuffer after D2H. “All host data is opaque tiled data” would therefore be too broad. Preserve representation when compatible; convert when the consumer requires it.

Self-test, with short answers
    

  • “Zero-copy means zero PCIe traffic.” No. Aliasing an existing buffer can remove an intermediate copy; host↔HBM DMA still moves the payload.
    • 

  • “A successful D2H means the CPU can interpret the result as ordinary floats.” Only if the representation contract says so. Raw KV bytes can preserve device tiling/padding.
    • 

  • “Keeping the tensor alive prevents races.” It helps lifetime, not conflicting accesses or ordering.
    • 

  • “A future became ready, so it succeeded.” Check its completion status; the Python await wrappers surface errors.
    • 

  • “Eight visible devices means eight v7x packages.” Device exposure and package count differ; inspect topology and process visibility.
    • 

  • “An offload pool enlarges VMEM.” It adds host capacity. It does not grow on-chip scratchpad.
    • 

  • “A CPU PJRT mock test proves v7x behavior.” It verifies some plumbing. Real layouts, DMA registration, and hardware overlap require device validation.
    •
