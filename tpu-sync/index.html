基础讲义

我们要做成什么：给 TPU 上的 KV cache 拍快照

这份讲义围绕一个任务展开：把 TPU 上暂时不用的一块 KV cache 保存到 CPU 内存，之后恢复到模型实际读取的位置，并证明恢复已经完成。

假设你在运行一个聊天模型。模型每生成一个 token，都要访问先前 token 的 attention key 和 value。把这些结果留在设备内存中，就不必重新计算；这份保留的数据叫 KV cache。请求越多、上下文越长，缓存占用越大。暂停的请求暂时不需要计算，但它的缓存仍然占着昂贵的设备内存。

一种办法是把暂停请求的缓存搬到容量更大的 CPU 内存，需要继续生成时再搬回来。这就是本讲义的出发点。我们先研究单机的一次往返，不从分布式调度、构建系统或编译器术语开始。

模型在 TPU 上生成 KV 数据
          ↓ D2H：device → host
CPU 保存快照；确认复制完成后，原设备区域才可能被复用
          ↓ H2D：host → device
把快照恢复到指定设备区域；确认完成后，模型继续读取

为了方便调度，系统把缓存划分成 block。它是软件定义的一组缓存数据，不是 TPU 硬件的计算 tile；一个 block 也未必对应一条 DMA 请求（由传输引擎执行的内存搬运）。后面我们会算出它究竟对应哪些字节。

读者只需熟悉普通 PyTorch tensor 和 CUDA 的基本内存操作。正文会在需要时解释新名词。没有 TPU 也可以完整阅读和操作网页示例；标为硬件实验的代码才需要兼容的 TPU 环境。文中的数字示例是教学模型，不冒充实机测量。

先画出数据住在哪里

在 CUDA 中，你会区分 CPU RAM、GPU global memory 和片上 shared memory。TPU 同样有多层存储：远处的容量大，靠近计算单元的容量小但适合反复访问。我们要给 KV cache 找一个临时住处，首先需要知道它现在在哪里。

HBM 是设备侧的高带宽内存，承担类似 GPU global memory 的角色。VMEM 是 TPU 片上的向量暂存内存；内核把要复用的数据搬进去，再交给计算单元。MXU 是矩阵乘法单元。还有供标量工作使用的 SMEM；暂时不需要背它的容量。

这里有两种不同的“复制”：我们把缓存从 CPU 搬到 HBM；执行 attention 的内核再安排 HBM 到片上存储的数据供给。后者速度很快，并不意味着前者也同样快。CPU 与 TPU 的连接、HBM 本身的带宽、TPU 芯片之间的 ICI 连接，是三个不同资源。

v7x 的存储范围阅读时怎样理解
一个物理封装有两个 chiplet，合计 192 GiB HBM不是每个运行时可见设备都能任意分配这整个容量
每个 chiplet 约 96 GiB HBM，约 3.7 TB/s HBM 带宽这是设备内部访问 HBM 的量级，不能直接代入 CPU↔TPU 复制时间
每个 TensorCore 有 64 MiB VMEM比 HBM 小很多，用来服务当前计算，不能当成卸载缓存的目的地

例如，把 32 MiB 缓存卸载到 CPU，至少要通过主机与设备之间的链路搬运这些字节。估计耗时要用该链路的有效带宽；要判断值不值得，还要与重新计算这份缓存的代价比较。第一节会完整算一次。

同样是 H2D：创建 tensor 与恢复快照有什么不同？

这里使用 Google TorchTPU：它让 PyTorch 操作通过 TPU 后端执行。先用普通框架接口创建缓存，再考虑如何恢复已经保存的原始字节。这两种操作都把数据送进 HBM，但调用方承诺的内容不同。

第一次：把逻辑数值放到设备

cache = cpu_tensor.to("tpu")

你给出数值、形状和类型。框架后端负责取得合适的设备存储，并安排必要的表示转换。例如 CPU 上连续排列的元素，在设备上可能采用带分块或填充的表示。你不必自己拼出这种表示。

之后：恢复已有存储的字节

manager.h2d(...)

manager 已经持有缓存的目标存储。你给出之前保存的兼容物理快照，以及要恢复的 block 映射。它将这些信息转换成字节区间，写入现有分配；不会把任意 CPU 数组自动解释成正确设备布局。

举个反例：你把六个 float 按 CPU 顺序写进一块内存，直接把 24 字节 raw-copy 到一个逻辑上有六个元素的设备 buffer。即使复制完成，也不能据此证明 tensor 正确：设备表示可能包含 padding，元素位置也可能不同。第二节会用小矩阵逐个画出这种差异。

因此，最稳妥的第一项实验是往返恢复：普通接口上传已知数值 → D2H 保存实际物理字节 → 修改设备数据 → H2D 恢复同一份快照 → 普通接口读回并检查数值。这样先学会复制，不必先发明设备布局。运行时对主机内存的要求仍须满足。

还有两个独立问题：目标是不是模型实际读取的那份分配？模型是否会在复制结束前抢先读取？前者是存储身份，后者是执行顺序；分别在第三和第六节解释。

第 1 课

先决定：这块缓存值得搬到 CPU 吗？

假设你正在服务一个长对话。对话暂时停了，但它的 KV cache 仍占着 TPU HBM；另一个请求又需要这块空间。你有两个选择：丢掉缓存，下次重新计算；或者暂存到 CPU 内存，下次搬回来。我们先算清楚第二种选择的代价。

先区分“存得下”和“取得快”

KV cache 保存注意力计算已经产生的 Key 和 Value。它通常放在 HBM，因为后续生成 token 会继续读取它。TPU 片上的 VMEM 则是计算过程中使用的局部工作存储，不是给整个长对话永久存放缓存的地方。把 KV 搬到主机 DRAM，是用已有的主机容量承接暂时不用的缓存，让 HBM 区域在卸载成功且没有其他使用者后可供别的请求复用；下次使用前，仍然需要走主机与 TPU 之间的数据通路搬回 HBM。

这与 CUDA 中把缓存从 GPU 显存卸载到 CPU 的动机相同。HBM 的本地带宽再高，也不能代替 host↔HBM 的传输带宽；计算矩阵乘时的 HBM↔片上存储流量又是另一条路径。

算一个可以检查的例子

假设模型有 32 层、每层 8 个 KV heads、head dimension 为 128，K 和 V 都用 BF16，每个数 2 字节。先忽略分片和 padding：

每个 token 的 KV = 2（K、V）× 32 × 8 × 128 × 2
                  = 131,072 bytes = 128 KiB
一个 256-token 缓存块 = 256 × 128 KiB = 32 MiB

这是整个模型的有用数据量。若模型分布在多块设备上，应根据实际分片计算当前设备要搬多少，不能直接把这个数当成每设备大小。

现在假设这次恢复的有效带宽是 25 GB/s，提交开销是 15 μs。这两个数只是教学假设，不是 v7x 实测结果：

32 MiB = 33,554,432 bytes
恢复时间 ≈ 15 μs + 33,554,432 / 25,000,000,000 秒
         ≈ 1.357 ms

如果重新计算相同前缀需要 8 ms，恢复看起来有利；如果只需 0.8 ms，恢复反而更慢。这个比较还没有计入排队、其他块的传输，以及尚未付出的卸载成本。提前预取可以隐藏一部分等待，却不会消除带宽消耗。

读完本课，你应能做的判断：“CPU 内存更大”是容量理由；“恢复比重算快，而且赶得上下一次 attention”才是延迟理由。仓库里的 raw transfer 就是把后一个过程做成可控的字节搬运。源码背景：raw transfer 概述。

练习：1 GiB 数据走同样的 25 GB/s 链路，单向至少需要多久？

只算数据时间：1,073,741,824 / 25,000,000,000 ≈ 42.95 ms。卸载再恢复约 85.90 ms，还没有计入提交和排队。不能把 TPU 本地 HBM 带宽代入这个主机传输公式。

第 2 课

复制回来的字节，为什么不像原来的 tensor？

你已经把一块 TPU 缓存复制到 CPU。复制成功了，但把接收内存强行当作连续 float 数组查看，数值顺序却不对。先别怀疑 DMA：你可能把设备的物理存放顺序，误当成了 tensor 的逻辑元素顺序。

同一个矩阵，可以有两种地址算法

逻辑 tensor 告诉你元素的 dtype、shape，以及“第 r 行第 c 列”的意义。设备存储还要决定这些元素实际放在哪里。为了让计算按规则批量读取，后端可能把相邻元素组织成 tiles，并补齐不完整的边界。Padding 占空间，却不代表新的逻辑数值。

看一个 6×6 的 FP32 矩阵。CPU 普通行优先排列需要 6×6×4 = 144 字节。教学例子把它切成 4×4 tiles，边缘补到 8×8，再依次存放四个 tile，于是占 8×8×4 = 256 字节。这来自仓库的 Padding2D 测试，不是所有 v7x tensor 的固定布局。

元素 (4,1)：
普通行优先： (4 × 6 + 1) × 4 = 100 bytes
分 tile：tile 编号 2、tile 内元素编号 1（均从 0 开始）
         (2 × 16 + 1) × 4 = 132 bytes

所以我们要区分两种“上传”

cpu_tensor.to("tpu") 的输入是逻辑 tensor，框架/后端负责所需的设备表示转换。raw H2D 的输入则是一串已经符合目标表示的字节，复制接口不会猜测它们代表哪个矩阵。最简单可靠的学习实验是：从相容的设备布局 D2H 保存原始快照，再原样 H2D 恢复。

第 3 课
复制成功了，模型为什么还读到旧缓存？


假设 H2D 已经完成、字节也正确，但 attention 仍然使用旧的 KV。一个容易漏掉的问题是：你是否写进了模型真正读取的那块存储？完成事件只能证明请求结束，不能证明你选对了目标。


Tensor 是描述，storage 才是落点


PyTorch 的 view 可以让多个 tensor 描述同一份 storage。但在带有设备布局的后端中，如果你请求把一个重新解释布局的 view 实体化，它可能需要单独的设备分配。此时就出现两份数据：


原始缓存 storage A  ← 模型继续读取这里
       │
       └─ 某个 view 实体化为独立 storage B
                                  ↑
                           你的 H2D 写在这里


DMA 到 B 完全可能成功，A 却一个字节也没改变。并非所有 view 都复制；问题在于这次取 buffer 的过程是否产生了不同分配。因此适配器使用 GetBaseTensorBuffer(tensor) 沿着 storage 找回 A，而不是先让任意 view 变成一个独立 tensor。


把三个名字放回各自的位置


base_ref 是拥有存储引用的 TensorBufferHandle，不是裸 HBM 地址。它让适配器能够请求设备 buffer，同时保留原始存储的生命周期。PjRtBuffer 是运行时管理这块设备存储的对象；raw alias 则提供按字节区间访问同一存储的接口。它们是主机侧 handle，真正的缓存字节仍在设备 HBM。


tensor
  → GetBaseTensorBuffer：找原始 storage，得到 base_ref
  → base_ref.Materialize：提交尚未实体化的 base 工作
  → base_ref.AwaitBuffer：取得其运行时 buffer
  → RaidenBufferHandle::Acquire：建立 raw 访问所需的句柄
  → 保留 base_ref 和 raw handle，直到相关使用结束


这段顺序同时解决“找哪块内存”和“内存是否已经准备好”，但不会自动安排所有未来的模型读写。UnpackTorchTensor 原始实现还会检查 TPU device、连续性、storage offset 为 0、覆盖完整 storage，以及支持的 block-major 形状关系。它不接受任意切片；cache[10:20] 不能因为是 view 就直接套进这条路径。


RaidenBufferHandle 隔离不同运行时句柄形式，让下面的复制代码统一处理偏移、长度和完成。这样，识别 Torch storage 的知识留在适配器里，搬字节的代码不必理解每一种 tensor view。raw buffer 封装。


练习：保留 base_ref，是否就能保证模型与 DMA 不发生竞争？
不能。保留引用回答“存储还存在吗”；找到 base 回答“是不是那块存储”；等待生产者和复制完成回答“现在能读写吗”。如果模型正在写 A，而 D2H 同时读 A，保留引用也不会让快照自动一致。第 6 课会把这个时间顺序画出来。


第 4 课
给 CPU 上的缓存快照准备一个家


现在我们知道从 TPU 哪块 storage 读取。接下来要把它搬到 CPU。你写下一个 void* dst，复制接口却不会替你回答：这块内存是谁申请的、设备能否访问、什么时候可以释放。本课把这三个问题逐个解决。


第一步：确实有地方接收这些字节


假设快照需要 32 MiB。先申请至少这么大的主机内存，记录起始地址和容量；偏移加长度不能越界。仓库的普通 XLA 主机分配路径把分配大小向页边界取整，然后用 mmap 获得内存。分配回答的是“CPU 地址空间中，接收区在哪里？”


第二步：让运行时建立 DMA 所需的映射


CPU 能解引用一个地址，不等于设备的 DMA 路径已经具备使用它的条件。该分配器接着调用 PjRtClient::DmaMap(ptr, aligned_size)，把这段范围登记给运行时。你可以联系 CUDA 的 host registration 来理解其目的，但具体的 pinning、映射和访问要求应以当前运行时契约为准。页对齐本身不等于已注册，申请内存也不等于已锁页。


第三步：直到最后一个使用者结束，才拆掉这个家


异步提交返回后，设备可能还在往接收区写。立即释放它，会让进行中的 DMA 使用已经失效或被重新分配的内存。因此仓库返回的不是一个孤立指针，而是含指针、大小和共享 owner 的 HostBufferAllocation。owner 最后释放时执行 DmaUnmap 和 munmap；调用方必须确保它活过所有相关操作，且负责映射的 client 也仍有效。


申请主机范围 → DmaMap 注册 → 提交 D2H → 等待成功完成
                                             ↓
                                      CPU 快照可以使用
                                             ↓
                     后续 H2D / 网络发送等所有读取结束
                                             ↓
                              DmaUnmap → 释放主机范围


你可以在 host_memory_allocator.cc 中逐行找到这条生命周期，在 HostBufferAllocation 中看到三个字段。这里不是建议你到处手写注册；学习其原因之后，应优先复用仓库已有的分配器。


为什么又要做一个 pool？每次传一个 block 都重复申请和注册会增加开销。预先准备多个可复用槽位，传输只选槽位就好。代价是这些槽位常驻占用主机容量，而且“内存还在”不代表“可以覆盖里面的内容”。下一次 H2D 若还要读这份快照，就不能提前复用。


进一步理解：NUMA 与另一条 pinned_host 路径
多 CPU 插槽主机上，内存物理位置会影响到 TPU 的路径。设备感知分配器尝试设置 NUMA 策略并触碰页面；是否成功需要查看拓扑和日志，不能仅凭调用了接口就认定数据已在本地节点。另一个 RawHostBuffer 抽象先尝试 PJRT 的 pinned_host memory space，再回退到 host allocator；它与这里的 mmap/DmaMap 不是同一条构造路径。RawHostBuffer 实现。


练习：D2H 已结束，马上把接收槽位清零，稍后再用它恢复缓存，为什么错？
D2H 完成只说明快照已经到达。清零会破坏下一次 H2D 所需的源数据。即使指针、注册和 owner 都仍有效，恢复也只会搬回错误内容。只有不再有任何计划保留的快照或未完成读取依赖该内容时，槽位才能复用。


第 5 课
真正搬一次：把设备块 0 恢复到块 1


前四课回答了“搬什么、存在哪里、怎样保住内存”。现在把这些连接起来：设备缓存有四个块 A、B、C、D。我们把 A 和 C 保存到主机，再分别恢复到设备块 1 和 3。最后模型看到的应该是 [A,A,C,C]。


块编号是名字，DMA 最后需要字节范围


主机槽位和设备块是两套编号。假设某一层的实际物理 block 宽度为 R = 8,192 bytes，从设备块 2 保存到主机槽 5：


D2H：读设备 offset = 2R = 16,384
     写 host_base + 5R = host_base + 40,960
     长度 = R = 8,192
H2D：以后从该主机槽恢复到设备块 1
     读 host_base + 40,960，写设备 offset = 8,192


这个 R 是算术示例，不是下方程序保证采用的大小。manager 从每一层自己的物理分配大小计算行宽；不同层可以不同。raw 复制不理解 A 是哪段对话，是调用者决定编号的映射。物理行宽、Python d2h/h2d 接口。


读懂实验，再决定是否运行


下面实验需要可用 TPU、已安装的 Google TorchTPU 和匹配构建的 TPU Sync 扩展。它组合了固定仓库版本的公开 Python wrapper 与 Torch C++ 绑定测试中使用的形状，并非原样复制一项已经在本环境执行过的测试；本讲义未在 TPU 硬件上执行它。请在已配置好的 TPU 环境中运行；需要构建仓库时参考依赖与构建说明。没有 TPU 也可以完整推演结果。首次运行时独占这份 cache，不启动并发模型计算，并保留所有对象到最后一次等待结束。


把下面程序保存为 kv_roundtrip.py，在上述环境中执行 python3 kv_roundtrip.py。shape=(4,128,8) 的首维表示四个 block；其余维度是本实验的数据形状，不是 v7x 固定的 KV 或 tile 形状。
arange 为每个位置填不同的数，便于发现错位；全填 0 的测试会掩盖很多复制错误。.to("tpu") 负责初始 tensor 放置，manager 保存的是设备物理字节，最后的 .cpu() 再由框架转换回来做数值校验。每个 .Await() 都明确等待该次复制结束。


import torch
import torch_tpu  # 注册 Google TorchTPU 后端
from tpu_sync.api.torch.kv_cache_manager import KVCacheManager

# 每个位置使用不同数值，避免常数填充值掩盖错位。
shape = (4, 128, 8)
reference = torch.arange(4 * 128 * 8, dtype=torch.float32).reshape(shape)
cache = reference.to("tpu")
torch.tpu.synchronize()  # 等待生产者结束，再进入 raw copy 实验。

manager = KVCacheManager(
    kv_caches=[cache],
    local_control_port=0,
    max_blocks=4,
    num_slots=1,
    unsafe_skip_buffer_lock=True,
)

# 调用者负责独占访问：没有并发模型任务，不替换或修改 cache storage，
# 并且等待每一次复制完成。
manager.d2h(src_offsets=[0, 2], dst_offsets=[0, 1]).Await()

snapshot = manager.read_block_bytes(layer_idx=0, block_id=0)
print("raw bytes in one host block:", len(snapshot))
# snapshot 保留设备布局，不能直接当作 CPU float 数组。

manager.h2d(src_offsets=[0, 1], dst_offsets=[1, 3]).Await()

expected = reference.clone()
expected[1] = reference[0]
expected[3] = reference[2]
actual = cache.cpu()  # 由框架转换为 CPU tensor，进行数值校验。
torch.testing.assert_close(actual, expected, rtol=0, atol=0)
print("PASS: blocks 1 <- 0 and 3 <- 2; untouched blocks preserved")



预期第一行打印实际物理 block 的字节数，不应预先假设等于逻辑元素数乘 dtype 大小；所有断言通过后，最后一行打印 PASS: blocks 1 <- 0 and 3 <- 2; untouched blocks preserved。这同时检查了被覆盖的块和未修改的块。


local_control_port=0 是构造参数，本实验不研究网络。unsafe_skip_buffer_lock=True 明确把独占访问和排序责任交给我们，因此程序先同步生产者，再逐次等待；不能直接把这个例子与正在运行的模型并发混用。若本机版本或布局不兼容，先对照 仓库 Torch 绑定测试，不要靠去掉校验让实验“通过”。


练习：把 H2D 的 dst_offsets 改成 [3,1]，最终四块是什么？
D2H 后主机槽 0 是 A、槽 1 是 C。改成 [3,1] 后，A 写到设备块 3，C 写到设备块 1，所以得到 [A,C,C,A]。块 0、2 未变。src_offsets 和 dst_offsets 按位置配对，编号不是同一命名空间。


第 6 课
去掉等待之后，哪些字节会发生竞争？


上一课每次复制后都等完成，容易理解但不能重叠工作。现在你想先提交 D2H，再去做别的计算。这个优化从一个危险误解开始：函数返回，不等于字节已经到达。


用一块缓存画出时间线


假设模型正在写设备块 A，我们要把它存到主机槽 H，再恢复到设备块 B。若 D2H 在模型写完之前读 A，快照可能混入旧值与新值；若 CPU 在 D2H 完成前读 H，它也可能看到未完成的数据。顺序应当是：


模型完成对 A 的写入
        ↓
提交 D2H(A → H) ── 传输中：不能覆盖 A，不能读取 H ── 完成
        ↓
H 现在是一份可用快照
        ↓
提交 H2D(H → B) ── 传输中：不能覆盖 H，不能让模型读 B ── 完成
        ↓
模型才可以使用恢复后的 B


这里有三个不同问题。生命周期是 A、H、B 的分配还在不在；生产者就绪是源数据写完了没有；访问排序是复制期间有没有冲突，以及消费者何时开始。共享 owner 主要解决第一个问题，完成事件为某一次操作提供结束与状态信息，应用仍要把这些事件连成正确依赖。


PJRT C 复制接口返回 event，仓库再将完成结果交给 future/等待路径。必须检查错误；事件 ready 也可能代表失败。.Await() 是上一课选择的简单同步边界。raw 复制、事件和 future 实现。

第 7 课
同样 32 MiB，为什么拆成小块就慢了？


你测到复制一整段缓存很快，但实际 KV 请求由许多小块组成，吞吐突然下降。总字节数没变，为什么？因为系统不仅要搬数据，还要为每次提交准备描述、调度和处理完成。


先用一个简单模型定位问题


令 S 为总字节数，B 为有效传输速率，α 为每次提交的固定开销。如果 n 次提交串行执行，暂时忽略重叠：


一次大传输：T₁ ≈ α + S/B
n 次小传输：Tₙ ≈ nα + S/B


取教学假设 S=32 MiB、B=25 GB/s、α=15 μs。数据本身需要约 1.342 ms。一次提交总计约 1.357 ms；拆成 64 次则约 1.342 + 64×0.015 = 2.302 ms，有效吞吐约 14.58 GB/s。差别来自额外的 63 次固定成本，而不是我们把物理链路变慢了。


什么时候能合并？


设备块 [2,3,4] 放到主机槽 [8,9,10]，如果双方物理块宽相同且连续，可以表达成一个更长的范围；若它们去往 [8,30,10]，目标不连续，就不能直接用一个连续 DMA 代替。一个 batch API 也不保证最后只有一次硬件提交，应看实际实现和测量。


下面保持总数据量不变，只改变提交数。再把 α 调高，观察小块场景为什么更受影响。这里所有数字都是可调教学输入，不是 v7x 跑分。

第 8 课
从一块快照，走到真实 KV 传输引擎


现在我们已经讲通了保存和恢复一个连续块的过程。真实引擎还会遇到两个变化：缓存块中只有部分区域有用；目标缓存可能在另一台主机。我们沿用前面所有规则，只扩展“要搬哪些范围”和“经过哪些端点”。


一个 block 不一定是一整段有用数据


假设一个 pool 的基址偏移是 8，每个 block 相隔 128 字节，但每块只使用两个 16 字节区域，分别从块内偏移 0 和 32 开始。把 storage、块间距和区域表分开描述，通用复制代码就无需知道这里存的是 attention KV 还是另一种模型状态。


全局偏移 = pool_base + block_id × block_stride + region_offset

block 0：8 + 0×128 + 0  → (8,16)
         8 + 0×128 + 32 → (40,16)
block 1：8 + 1×128 + 0  → (136,16)
         8 + 1×128 + 32 → (168,16)
每对数字是（起始字节偏移，长度）


实际 payload 是 64 字节，最后一个范围结束于偏移 184；从第一个有用字节到最后结束的跨度则是 176 字节。三者不是同一个大小。该例对应 PoolSpec / RegionSpec及 范围计算测试。这种抽象的目的，是由模型适配层描述数据结构，再由传输层检查边界并搬动字节。


另一台主机不是“再加一个设备指针”


仓库展示的一条跨主机路径是：


源 TPU HBM → 源主机 DRAM → 网络 → 目标主机 DRAM → 目标 TPU HBM
            等 D2H 完成           等网络接收完成       等 H2D 完成


名字叫 device-to-device，只说明两端是设备；这条实现仍通过两边的 host staging，不能据名字认定走了直连 ICI。示例中的路径说明、host socket transport。


若完全串行，一块 S 字节的时间近似为 S/B_D2H + S/B_network + S/B_H2D + 开销。多个独立块可以流水执行，但稳态吞吐仍受最慢阶段以及共享主机内存等资源限制。网络读完源 staging 之前不能覆盖它；目标 H2D 完成之前不能让 attention 消费新缓存。


把本讲义收束成一个设计


对于你的 Rust 引擎，控制面给出“哪块缓存去哪里”；设备后端接收存储 handle、字节范围、完成依赖，并返回可检查的完成结果。Torch 适配器负责把活的 cache storage 交出来；运行时负责执行复制；传输对象保留所需 owner。模型布局、传输调度、实际字节搬运因此可以分别理解，又在明确的边界上连接。


最后做一个闭环检查：从逻辑 KV 数量推算有用字节，从真实布局得到物理范围，验证目标是模型使用的 storage，准备主机槽位，安排 producer→D2H→H2D→consumer，再用框架逻辑读回验证。没有硬件时能完成前五项推演；最后的设备数值校验必须明确留待实测。原始 KV 快照保留布局；若用途变成权重转换，则可能需要显式 TileBuffer/DetileBuffer，见 权重同步实现。


综合练习：上面两个 block 的四个 live regions，只分配 64 字节并照原偏移写入，行不行？
不行。64 是有效载荷总量，不是保留这些偏移所需的容量；最后一个范围需要写到 184 的结束位置。可以把四段打包成紧凑的 64 字节，但必须另存映射，并在恢复时分别散写回原来的范围。打包节省空间，却增加描述和复制工作。这正是范围抽象需要明确表达的取舍。

#include <dlfcn.h>

int main(int argc, char** argv) {

    return 1;
  }

    std::cerr << (error ? error : "null GetPjrtApi") << '\n'; return 1;
  }
  const PJRT_Api* api = get_api();
  if (!api || api->struct_size < PJRT_STRUCT_SIZE(PJRT_Api, extension_start)) {
    std::cerr << "missing API extension-list field\n"; return 1;
  }
  std::unordered_set<const PJRT_Extension_Base*> seen;
  bool found = false;
  for (auto* ext = api->extension_start; ext; ext = ext->next) {
    if (ext->struct_size < PJRT_Extension_Base_STRUCT_SIZE ||
        !seen.insert(ext).second) {
      std::cerr << "invalid extension chain\n"; return 1;
    }
    std::cout << "type=" << static_cast<int>(ext->type)
              << " bytes=" << ext->struct_size << '\n';
    found |= ext->type == PJRT_Extension_Type_RawBuffer;
  }
  std::cout << "extensions=" << seen.size()
            << " RawBuffer=" << (found ? "yes" : "no") << '\n';
  // Keep the plugin loaded until process exit. No client/device is created.
  return found ? 0 : 2;
}

把“复制一段字节”写成一次真正的 API 调用
现在假设模型已经在 TPU HBM 中有一块 KV cache。我们要把它备份到 CPU，之后恢复到原来的位置。这里暂时不考虑缓存淘汰策略，也不编译模型：目标只有一件事——向运行时说明从哪里搬、搬多少、什么时候算搬完。


第一步：得到操作已有存储的入口
普通 PJRT_Buffer 是表示张量存储的运行时对象；PJRT_RawBuffer 则让调用者按物理字节操作已有存储。通过 CreateRawAliasOfBuffer 得到的 raw alias 是同一块存储的另一个句柄，并没有新建一份 cache。可以把它理解成“给同一间仓库换一张按货架编号操作的通行证”。它不是 cudaMalloc：创建最初的设备 buffer 是另一个步骤。


这些句柄对象在 CPU 上；它们代表的字节可能在 TPU HBM。GetOnDeviceSizeInBytes 查询实际设备存储大小。它可能大于形状乘 dtype 的逻辑大小，因为设备布局可能含有 padding。先查询大小，再检查每次复制的范围。


第二步：为什么是一张函数指针表？
你的程序不必链接所有 TPU 内部函数。它加载 libtpu.so，调用公开入口 GetPjrtApi()，拿到主 API 表，再沿扩展链找到 raw-buffer 扩展。扩展表中的每个字段都是一个函数指针。PJRT 头文件规定签名和参数结构；加载的插件提供实际执行代码。
GetPjrtApi()                    // 公开入口
  → PJRT_Api*                   // 错误、事件、设备等通用操作
  → extension_start → ...       // 查找 RawBuffer 扩展
  → PJRT_RawBuffer_Extension*    // 原始字节操作的函数表
  → CopyRawHostToDevice(&args)   // 间接调用插件实现
函数指针就像一张明确写出来的 C++ virtual table。函数的名字不必作为动态符号公开；只要插件把地址放进表里，调用者就能按约定签名调用它。实际硬件复制由 libtpu 内部实现，不是由这份头文件、也不是由 TorchTPU 重写一遍。


第三步：把恢复请求装进 Args
假设 snapshot 已保存兼容布局的设备原始字节，且满足运行时的主机内存要求。下面是提交部分的示意，不是独立可运行程序；它刻意留下错误处理和等待，让你看清这次调用本身。
PJRT_RawBuffer_CopyRawHostToDevice_Args args{};
args.struct_size = PJRT_RawBuffer_CopyRawHostToDevice_Args_STRUCT_SIZE;
args.extension_start = nullptr;
args.buffer = raw_buffer;        // 恢复到哪个已有设备存储
args.src = snapshot;             // CPU 字节从哪里读
args.offset = device_offset;    // 目标中的字节偏移
args.transfer_size = byte_count;
PJRT_Error* error = raw_ext->PJRT_RawBuffer_CopyRawHostToDevice(&args);
// error != nullptr：提交阶段报错，读取并销毁 error。
// 否则保存 args.event，等待并检查最终状态后再复用 snapshot。
src 是普通主机地址；buffer 是不透明设备存储句柄；offset 和 transfer_size 的单位都是字节，不是 token、block 或浮点元素。event 是输出：它让我们知道异步工作何时结束，以及是否成功。extension_start 是参数结构的扩展入口，不是这里正在调用的 raw-buffer 函数表。


这个 entry-point 的 Args 没有依赖事件列表。因此，你必须在提交之前满足生产者完成的条件，并在完成之后才让下一位消费者读取。不要把它想成一个隐藏了 CUDA stream 参数的 cudaMemcpyAsync。


第四步：把它对应回 TPU Sync
代码里的 c_hold 指向一个保留资源所有权的 RawBufferHolder。c_hold->c_api 是通用 PJRT 表，用于错误与事件处理；c_hold->extension 是 raw-buffer 表。pjrt::PjRtCApiRawBuffer_CopyRawHostToDevice(...) 是调用方的 C++ 便捷包装：整理 Args，调用插件，再包装结果。它和插件函数负责同一次操作，但不是同一个函数或同一层实现。
多块复制会产生多个事件。TPU Sync 将它们和需要保留的 buffer holds 放进完成对象，直到工作结束。这里必须分别检查“已经完成”和“完成成功”。提交第二块失败，也不能丢掉第一块已经开始的复制所需的内存。


顺着一条路径阅读：RawBufferHolder → 取得 raw handle → 提交 C event 复制 → 保留事件和资源。接口原文：raw-buffer 头文件；调用方包装：C++ helper。上游 main 会变化，开发时应匹配实际运行时。


补充实验：这个接口在 libtpu 二进制里真的存在吗？
本讲义检查了 PyPI 的 libtpu 0.0.48 Linux x86-64 二进制：调用 GetPjrtApi 后沿链读到 17 个 advertised extensions，其中包含 RawBuffer。所检查的扩展表有七个函数槽，复制相关的两个是 H2D 和 D2H；其余是建立 alias、销毁、查询大小、查询 memory space、查询 host pointer。
检查还将 H2D 函数指针减去共享库加载基址，与内部符号偏移 0xc75a4e0 对上。这证明函数表指向二进制中的实现代码，并不证明 TPU 上的 DMA 已执行。不同版本的扩展数量、布局和能力可能不同。整个二进制内部也远不止两个复制函数。
这个补充只回答“接口是否出现在被加载的插件中”。实际复制是否支持你的设备、注册方式和对齐要求，要靠下面的硬件实验验证。


检查理解：为什么 raw alias 的创建很快，却不代表 D2H 不搬数据？
创建 alias 只是建立另一个访问已有存储的句柄；D2H 则必须把选中的字节从设备搬到主机。两件事发生在不同步骤。

把已经跑通的复制接到 Rust KV 引擎
当你在真实 TPU 上跑通一块缓存的快照恢复后，下一步是把这项能力接入现有引擎。现有 Rust 控制平面只想表达：“把请求 A 的 block 3 备份到主机槽位 5。”它不应该知道 TPU 的物理 tile，也不应该收到一个伪装成 CUDA 地址的 TPU 句柄。我们需要一个适配层，把这个业务动作翻译成正确的复制。


先保留“选哪块”，再替换“怎么搬”
缓存键、淘汰策略、请求调度可以继续使用原来的代码。TPU backend 接管三件事：取得模型正在使用的存储；把 block 编号转换为物理字节范围；提交复制并返回可观察的完成状态。这样控制平面继续决定搬什么，数据平面负责搬对。
例如布局描述明确给出 block stride 为 128 字节，每块有两个有效范围 (0,16) 和 (32,16)。block 3 对应 (384,16) 和 (416,16)。这是算术教学例子，不是 TPU 的固定布局；真正的 stride 和范围必须来自所支持的 cache 布局，并按层、按 shard 处理。


为什么需要一个小 C++ 桥？
独立实验可以自己创建 PJRT client。接入 TorchTPU 模型时，应使用模型已有的 runtime/client 和 buffer。C++ 桥从 at::Tensor 取得 base storage，并保留框架所有者；Rust 只接收不透明的 C handle。不要让 Rust 直接猜测 ATen 对象或 XLA C++ future 的内存结构，也不要假设新建 client 能操作另一个 client 的 buffer。
base_ref 是保留原始存储的框架句柄，不是裸 HBM 指针。它让模型实际使用的分配保持存活；raw alias 让复制接口访问那块分配。这两层职责相关，却不是同一个概念。


最容易遗漏的设计：调用者不等了，复制归谁管？
Rust 调用者可能因为请求超时而 drop future。设备不会因此自动取消 DMA。如果 drop 顺便释放 host snapshot，正在进行的 H2D 可能继续读取已经失效的地址。因此需要一个引擎自己保留的 in-flight 记录，与用户持有的等待 ticket 分开。
// 设计草图：不是已实现或可直接编译的 Rust API。
struct InFlightTransfer {
    device: Arc<DeviceAllocation>, // 框架 owner、raw alias、所属 runtime
    host: Arc<HostRegion>,         // 主机分配与必要的注册
    completion: PjrtEvents,        // 已提交操作的完成事件
}
// 引擎保存 InFlightTransfer，调用者只持有观察结果的 ticket。
// ticket 被 drop 后，记录仍保留至原生工作完成且资源可安全释放。
Arc 解决共同所有权，不解决读写竞争。模型写完之后才能 D2H；H2D 成功之后模型才能读；网络还在读的 host slot 也不能复用。不要未经运行时契约检查就为 FFI handle 声明 Send/Sync。
模型最后一次写入结束 → D2H → 检查成功 → 主机快照可用
主机快照保持不变     → H2D → 检查成功 → 模型下一次读取
第一版可以显式等待，以牺牲重叠换取易验证的顺序。之后再加入运行时支持的依赖集成。基本 raw-copy Args 并不直接接受你设计的 Rust dependency 参数；适配层必须真的实现这个参数的语义。


恢复成功，需要比“大小一样”更多的信息
快照应伴随 shape、dtype、物理布局/padding、sharding 和兼容性标识。长度相同的两份字节不一定能互换。另一个 generation 标识可以检测模型是否替换了原有分配：布局兼容性回答“这些字节能否用于这个布局”，generation 回答“这还是我之前注册的那块存储吗”。
批量提交若只成功了一部分，保留并等待已提交部分，整体返回失败，不把半份快照发布为可用。恢复失败时，不能让 attention 读取部分更新的 cache。关闭引擎时先排空在途操作，再释放注册、owners 和 runtime。
先验收一件具体的事：恢复后模型读到正确值，邻近 block 没被破坏。之后再做取消、部分失败、分配替换测试，最后优化并发、合并和吞吐。NVIDIA 原始快照不能默认直接恢复到 TPU；跨后端需要规范化表示和转换。

一次复制会经过谁？先认识三个角色


写下 cache = cpu_tensor.to("tpu") 时，你提出的是“让这些数值存在 TPU 上”。Python 本身不驱动硬件：TorchTPU 把 PyTorch 的请求交给 TPU 后端；运行时负责创建存储和执行操作。PJRT 是访问这些运行时能力的接口，TPU 的实现由 libtpu 提供。


XLA 的核心角色不同：它把张量计算变成可执行程序。例如模型需要计算矩阵乘法，编译器决定怎样组织计算和数据；而把已有设备存储的某一段原始字节复制到主机，是运行时操作。仓库依赖 XLA 代码，不代表每次复制都重新编译模型。


要计算：张量运算 → 编译器生成程序 → 运行时执行程序
要搬运：已有 buffer + 源/目标范围 → 运行时提交复制 → 等完成
要构建：源码 + 头文件 + 依赖库 → 编译链接 → Python 可加载的 .so

第一次阅读时，不必把依赖树全学完。先带着一个问题进去：“manager.h2d(...) 收到 block 编号后，在哪里变成字节范围？”一次只跟踪一条调用链，你会发现很多庞大的基础设施不在这次修改范围内。


从 Python 的一个动作跟到设备复制
api/torch/kv_cache_manager.py       Python 对外接口
    ↓
frameworks/torch/*module*           Python/C++ 参数转换与绑定
    ↓
frameworks/torch/torch_tpu_utils.cc  获取真实 base storage
    ↓
kv_cache/*manager*、pool_layout     block ID → 物理范围
    ↓
core/raw_transfer_core.h            调用运行时、保留资源、观察完成
这里出现的 nanobind 是 Python 与 C++ 之间的绑定工具；at::Tensor 是 PyTorch 的 C++ 张量对象。它们负责把调用送到正确层。复制核心不需要理解 Python 对象，也不应该由网络传输层去猜张量布局。这就是将 framework adapter 与 raw copy 分开的理由。
如果失败发生在 import，先查 loader；若复制成功但模型看到旧值，查 base storage；若块顺序错了，查范围构造；若提前复用了 host slot，查事件和 owners。先用症状定位一个边界，再顺着它读，不需要从仓库首页读到最后。


准备修改与构建时再读：API、ABI 和 XLA pin
API 规定源码如何调用。ABI 规定编译后的二进制如何相互理解，例如结构布局、符号名、调用约定以及 C++ 虚函数表。头文件能编译，不代表它一定匹配另一个版本的运行库。
TPU Sync 会接触 TorchTPU 创建的 C++ PJRT 对象，因此 build.sh torch 解析 TorchTPU 所用的 XLA revision，按该版本构建。仓库默认的 JAX XLA pin 不能随便替代它。原始复制完成路径使用 C events，也是在减少分别构建的 XLA C++ future 对象跨库交换的问题；它没有消除其余 C++ ABI 要求。
如果你要编译仓库，才需要记录 Python、Torch、TorchTPU、libtpu 版本、仓库 revision、TorchTPU 的 XLA pin 和实际加载的扩展变体。这个清单是排查环境的依据，不是理解一次 D2H 的前置课程。所引用 snapshot 的 Torch wheel 要求 libtpu>=0.0.47，注释关联 multiprocess v7 DmaMap 修复；应选择相容环境，而非任意替换为最新版本。
Torch XLA pin · 运行时依赖 · 共享库加载 · C event 的 ABI 动机。

实践与参考
学完之后，用一次故障检验自己的理解
不要求背缩写。对下面每个场景，先写出原因和修复方向，再展开答案。你应能把答案落到某块内存、一个所有者或一条先后关系上。


1. H2D 返回成功，但模型读到旧 cache。首先怀疑什么？
先区分提交成功和最终完成成功。如果都成功，再确认写入的是模型实际使用的 base storage，而不是 view 的独立物化副本；检查偏移、目标 block 以及模型读取是否排在复制之后。DMA 成功只证明所提交的操作成功，不证明选对了目标。


2. D2H 得到 4096 字节，我能直接把它看成 1024 个 float 吗？
不能仅凭长度判断。原始字节可能含 tile 布局和 padding，dtype 也未必是 float。需要布局契约，或者通过正常 tensor 读回路径得到逻辑值。保存原始快照不要求 CPU 能解释每个值。


3. Rust 请求超时，drop ticket 后能回收 host slot 吗？
不能直接回收。取消等待不代表 DMA 停止。引擎仍需保留记录与资源，直到所有会访问该区域的复制或网络操作结束。否则新请求可能与旧 DMA 读写同一内存。


4. 两个 block 在设备上连续，可以合成一次复制吗？
还要检查主机侧也连续且映射顺序相同，以及边界、对齐、权限和生命周期是否兼容。只看设备连续不足以决定合并。


5. GetPjrtApi 返回 RawBuffer 表，是否证明我的 TPU 可复制？
只证明该加载插件 advertised 这个接口。还需检查 ABI/字段可用性、设备和内存支持、对齐/注册要求，并实际创建 buffer、执行复制、等待与验证结果。无硬件 discovery 和真实 DMA 的证据范围不同。


6. 为什么 cpu_tensor.to("tpu") 和 raw H2D 不能互相替代？
前者请求框架创建/放置具有指定逻辑值的张量，后端负责必要的表示处理；后者把已有物理字节写进已有存储，要求调用者提供兼容表示。raw H2D 不会自动把任意 row-major CPU 数组变成正确的 TPU 布局。


最后写一段不超过十行的说明：为了让 attention 正确读到恢复的 block，你会保留哪些对象、等待哪些完成、检查哪些字节范围？能说明这些具体责任，就可以开始修改一个小的传输路径。
